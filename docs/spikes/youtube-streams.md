# Spike: где брать видеопоток YouTube (шаг 1 плана)

**Дата:** 2026-10-24 · **Код:** `spikes/youtube-stream/` · **План:** [plans/rinse.md](../../plans/rinse.md)

## Вывод

**Свой `<video>` с прямой ссылкой на поток (подход Vinegar) в октябре 2026 не работает ни на одной платформе.** YouTube больше не отдаёт HLS ни одному клиенту, а прямые ссылки без PO-токена отдают только первые ~12–16 МБ файла, дальше 403. Видео обрывается через несколько минут.

**Новое направление: оставить плеер YouTube и вырезать из него рекламу.** Из ответов плеера удаляются поля `adPlacements`, `adSlots`, `playerAds` (тот же приём, что `json-prune` в uBlock Origin). PiP и фоновое воспроизведение добавляются поверх родного `<video>`. Поток, PO-токены и SABR остаются заботой самого YouTube, поэтому подход не ломается от каждого изменения защиты потоков.

## Как проверяли

`node spikes/youtube-stream/probe.mjs` прогоняет 21 видео из 7 тем (музыка/VEVO, новости, игры, туториалы, детское, подкасты, 4K; список в `videos.txt`) в двух профилях:

- **iphone:** `m.youtube.com`, UA Safari на iPhone;
- **mac/ipad:** `www.youtube.com`, UA Safari на Mac. iPad Safari по умолчанию запрашивает десктопный сайт, поэтому профиль общий.

Источники: `ytInitialPlayerResponse` со страницы и `POST /youtubei/v1/player` с клиентами WEB, MWEB, IOS, TVHTML5, WEB_EMBEDDED_PLAYER, ANDROID_VR. Запросы шли с UA Safari, как их отправил бы скрипт на странице. Для каждой найденной ссылки проверялось, отдаёт ли она байты медиа.

Дополнительные проверки:

- `probe-native-ua.mjs` — те же клиенты с их собственным UA (расширение могло бы подменить UA через `declarativeNetRequest`);
- `probe-ios-deep.mjs` — форматы, скорость и конец файла для клиента IOS;
- `probe-threshold.mjs` — с какого байта начинается 403.

**Клиент IOS с родным UA** (`probe-ios-deep.mjs`):

- muxed-форматов (видео и звук в одном файле) нет ни у одного из 21 видео, только раздельные адаптивные дорожки;
- первые 4 МБ отдаются в 15 из 21 случаев, на 12–44 Мбит/с, и с UA Safari тоже (к UA ссылка не привязана);
- **конец файла: 403 в 21 из 21 случаев**;
- порог (`probe-threshold.mjs`, 1080p, 23,5 МБ): 206 до 12 МБ включительно, 403 начиная с 16 МБ.

Другие клиенты с родным UA: ANDROID_VR — LOGIN_REQUIRED (7 из 8), TVHTML5 — UNPLAYABLE, WEB с UA Safari 15.5 (`web_safari`) — HLS не отдаёт.

**Рекламные поля** (`adPlacements` / `playerAds` / `adSlots`) есть в HTML 9 из 10 watch-страниц на `www.youtube.com` и в 0 из 10 на `m.youtube.com`. Мобильная версия, видимо, получает рекламу отдельными XHR (`/youtubei/v1/player`, `get_midroll_info`). Их тоже нужно перехватывать.

## Почему прямой путь закрыт

Чтобы сделать свой плеер, пришлось бы:

1. генерировать PO-токен — запускать BotGuard (обфусцированную VM YouTube) в странице и подписывать запросы к googlevideo;
2. собирать видео и звук из раздельных дорожек через `ManagedMediaSource`;
3. расшифровывать `signatureCipher` и параметр `n` для форматов WEB.

Это фактически переписать плеер YouTube и чинить его при каждом обновлении защиты. Для MVP это неоправданный риск.

## Что проверить вручную в Safari (тестовое расширение готово)

Тестовое расширение — `spikes/youtube-stream/extension/`, Xcode-проект — `spikes/youtube-stream/xcode/Rinse Spike/`. Сборка проходит для macOS и iOS Simulator.

Расширение делает три вещи:

- вырезает рекламные поля из ответа страницы, `fetch` и XHR;
- скрывает от YouTube уход страницы в фон (`visibilitychange` и т.п.);
- показывает бейдж `rinse: N ad keys pruned` и кнопку **PiP** в правом нижнем углу.

Конвертер предупредил, что `"world": "MAIN"` не поддерживается, поэтому `content.js` внедряет `page.js` через `<script src>`. Дополнительно MutationObserver переименовывает рекламные ключи в inline-скрипте до его выполнения. Какой из двух механизмов успевает, видно в логах.

Чек-лист: iPhone, iPad, Mac; 5 видео на каждом, лучше те, где без расширения точно есть реклама.

- [ ] Бейдж показывает > 0, pre-roll не играет.
- [ ] Mid-roll на видео длиннее 10 минут не появляется (перемотать на середину).
- [ ] Переход на следующее видео без перезагрузки страницы тоже без рекламы.
- [ ] Не появляется попап «Ad blockers are not allowed» и нет зависания на чёрном экране.
- [ ] Кнопка PiP переводит видео в «картинку в картинке». Для iPhone это главный вопрос: плеер YouTube использует `ManagedMediaSource`.
- [ ] iPhone: свернули Safari или заблокировали экран — звук продолжает играть.
- [ ] В Web Inspector (Safari → Разработка → устройство) видны строки `[rinse:content] rewrote inline…` и/или `[rinse] pruned … from fetch player`. Записать, какой механизм сработал.

Как запустить:

- **Mac:** открыть Xcode-проект, схема `Rinse Spike (macOS)`, Run. В Safari → Settings → Advanced включить «Show features for web developers», затем в меню Develop → «Allow Unsigned Extensions». После этого включить «Rinse Spike» в Settings → Extensions и разрешить его на youtube.com.
- **iPhone / iPad:** в Xcode выбрать свой Team (Signing & Capabilities) для обоих таргетов, схема `Rinse Spike (iOS)`, Run на устройство. Затем Настройки → Приложения → Safari → Расширения → Rinse Spike → включить и разрешить на youtube.com.

## Что это меняет в плане

- **Шаг 6 «Плеер Rinse»** заменяется шагом **«Вырезание рекламы из плеера YouTube»**: перехват `ytInitialPlayerResponse`, `fetch` и XHR плюс CSS для рекламы в ленте.
- **Шаг 7** превращается в **«PiP, фоновое воспроизведение, устойчивость»**.
- Риск «YouTube начнёт вшивать рекламу прямо в поток (SSAI)» становится главным. Ранний сигнал — реклама при бейдже > 0. План Б в этом случае: детектировать рекламный отрезок по ответу плеера и перематывать его.
- Платформы: подход одинаков для iPhone, iPad и Mac. Различаются только источники рекламных данных (HTML на www, XHR на m.).
